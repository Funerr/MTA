# 转换交付与 GUI 宿主约定

这是 Skill 的输入输出约定，不是已经实现的 HTTP API、GUI 服务或 Runtime Schema。GUI 宿主负责加载 Skill、调用模型及文件工具，并呈现结果。宿主可以通过对话提供下列信息，不要求最终用户手填 JSON。

## 输入

- `project_root`：实际 MTA 项目。
- `sources`：已上传文件的可读取引用，或内联文本；附文件名/文档标识。
- `target_project`：配置中的目标项目；单设备平台或协作项目。
- `context`：应用、测试数据、设备角色及绑定、已知前置条件。
- `preferences`：用户明确的测试范围与允许变化，例如“仅验证拖动能力”；不使用全局“宽松模式”放弃硬性条件。
- `output_dir`：可选。
- 局部修订时带回前次草稿、转换记录、用户编辑和待回答问题的答案。

缺少会影响正确性的上下文时只阻塞相关用例；其他独立用例继续转换。未提供的平台不能由文件扩展名推断。

## 输出文件

建议以 `workflow.yaml`、`draft.json`、`conversion-report.json` 交付。没有就绪用例时不生成可执行 `workflow.yaml`，不要用空 `cases` 冒充有效工作流。

草稿顶层：`format_version: 1`、`cases`。每条草稿字段：

| 字段 | 内容 |
| --- | --- |
| `id` / `source_id` | 稳定内部标识 / 原编号（可能为空或重复） |
| `source_refs` | 文件与工作表/单元格范围，或 Markdown/文本行范围；保留原文片段 |
| `goal` | 测试目的 |
| `preconditions` | 条件及 `external` 或 `workflow` 的满足方式 |
| `data` / `device_roles` | 原始测试数据与明确设备角色 |
| `actions` | 稳定 ID、操作意图、必须保留的交互、允许的 UI 适配 |
| `expectations` | 稳定 ID、必须成立的结果、可接受变化、证据类型和来源 |
| `rewrites` | 原文、改写、理由、依据（用户要求/明确目标/待确认建议） |
| `issues` | 稳定问题 ID、受影响字段、问题及所需信息或缺失能力 |
| `status` | 下表中的逐用例状态 |

| 状态 | 含义与交付 |
| --- | --- |
| `ready` | 意图明确、每个预期均有可用证据路径、静态结构及 Node 输入检查通过；可导出，不代表执行通过 |
| `needs_clarification` | 缺关键上下文、来源歧义或要求矛盾；保留草稿 |
| `unsupported` | 所需运行或证据能力在当前契约中不存在或未得到验证；保留草稿与缺口 |
| `unvalidated` | 无语义阻塞，但缺少可用静态校验或检查失败待修复；仅供预览 |

转换记录包含：

- `format_version: 1`、源文件覆盖清单和目标项目。
- 每条用例的状态与问题，以及是否被纳入 YAML；报告总数、就绪数和排除数。
- `coverage`：来源预期 ID → 草稿预期 ID → 导出 case/step 索引（统一零基）及 Node；未覆盖项必须说明原因。共享断言必须能实际覆盖各预期。
- `rewrites`：每次实质性放宽、前置条件调整、推断及依据。
- `validation`：检查名称、`passed/failed/not_run`、实际证据和范围；注明设备与模型是否执行。只检查 YAML 可解析不能称为 Node 契约检查通过。
- `artifacts`：实际生成文件的位置。

## GUI 呈现与局部修订

呈现原文、意图和改写差异；执行 YAML 可展开。突出改变验收标准的建议，普通措辞调整无需逐项审批。先应用用户已明确的约束，再询问剩余的关键问题。

用户反馈通过用例/动作/预期/问题的稳定 ID 关联。只重生成受影响部分，保留用户编辑；同时重新检查相关覆盖关系及文件整体结构。删除或排除用例应有记录，不能在批量导出中悄悄丢失。

“转换”“导出”“执行测试”是独立操作。GUI 不因拿到 `ready` 自动执行 YAML；执行请求交给已有 MTA 运行入口。Skill 不提供自己的 Runner。
