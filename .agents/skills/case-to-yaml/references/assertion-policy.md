# 断言策略与示例

## 用业务结果约束 AI

判断一个细节是否可泛化，先问：改变它是否会使本测试失去意义？

| 细节 | 处理 |
| --- | --- |
| 控件位置、颜色、开关或下拉框 | 测试目标为功能状态时可泛化；若测试控件本身则保留 |
| 拖动终点 | 目标为可拖动时允许合理偏移；目标为定位精度时保留数值和规定容差 |
| 金额、计算结果、权限、业务对象、边界值 | 保留明确要求，不以 UI 漂移为由放宽 |
| “正常”“成功”“可用” | 从原文和上下文提炼可观察条件；无法确定时澄清 |
| 原文明确但疑似过严的阈值 | 给出改写建议和影响；无意图依据时保留原要求 |

容差必须来自用户、原用例或明确测试目的；不要随意发明百分比。可接受变化不能覆盖业务状态相反、目标对象错误或操作未生效。

## 证据类型

| 类型 | 所需证据 | 常见错误 |
| --- | --- | --- |
| 当前状态 | 当前页面可见且能识别目标状态的反馈 | 只看绿色、某个图标或页面标题 |
| 状态变化 | 同一设备、同一目标的前态和后态，及真实可用的比较路径 | 告诉单帧断言“比刚才变了” |
| 持续行为 | 不同时间点观测及明确的持续要求 | 用一次截图证明“一直播放” |
| UI 外业务结果 | 原要求需要的实际证据通道 | 用成功提示证明服务端到账 |

静态能力检查失败时标记 `unsupported`；信息缺失或歧义时标记 `needs_clarification`。证据不足不能变成通过。当前生产 `aiAssert` 沿用原生契约，不新增三态 Node。

前后观测还要排除替代解释：播放中的时间自然增长不能单独证明拖动有效；功能原本已启用不能证明“从关闭启用”成功。原用例验证状态转换时，必须保留前态要求；不能擅自改变播放器状态等前置条件来方便测试。

## 示例：功能启用

原文：在设置页点击“夜间模式”的开关，验证开关变绿。目标：验证夜间模式启用。

转换：页面反馈夜间模式已启用；入口形态和颜色不是硬约束。若原文实际目标是验证绿色视觉规范，则颜色必须保留。

以下为单设备表达示例，前置条件是已进入目标设置页；不是已通过的业务验收，也不作为实际文件直接交付：

```yaml
cases:
  - name: 启用夜间模式
    steps:
      - aiAct: >-
          在当前设置页面启用夜间模式，按实际提供的入口操作。
          入口可以是开关、下拉选项或其他控件；不要改变无关设置。
      - aiAssert: >-
          当前页面属于夜间模式设置，针对夜间模式的明确状态反馈
          表明它已启用，且没有与此结果相矛盾的未生效或错误提示。
          不要求特定控件形态、颜色或位置。
```

若无明确可见状态反馈，不能仅凭整体变暗断言成功。实际用例依据应用真实反馈选择可判定条件，不机械复制示例。

## 示例：拖动可用性

输入：“拖动到 50%，验证进度条可拖动。”用户补充：“不要求准确位置，主要验证拖动生效。”

- 操作：实际拖动进度控制区域到一个明显不同的位置，不以点击或输入数值替代拖动。
- 结果：拖动后目标进度或对应内容发生可归因于拖动的变化；允许终点偏移。
- 证据：同一目标的前后状态及拖动执行证据；考虑自然播放对进度变化的干扰。
- 交付：若当前契约无法把前后观测传入比较，保留意图草稿并标为 `unsupported`，说明缺的是比较链路。不要生成看似可执行的“相比刚才变了”断言。

反例：断言“当前存在进度条、播放器没有报错”。它没有验证拖动生效。

若输入为“验证定位精度，拖到 50%，误差不超过 2%”，必须保留阈值。若输入仅写“必须到 50%”但目的不明，保留要求并澄清。

## 示例：数值与多条件

“输入 1 + 2，结果为 3”：精确保留结果 3，不改为“出现计算结果”。

“保存联系人后回到列表，并能找到新联系人”：分别覆盖保存后的页面身份和目标联系人信息。现有联系人同名时，需要原文数据或可区分字段，不能仅用名字证明新增成功。

## 转换自检

用以下反事实检查草稿，而不是追求固定措辞：控件换了位置或类型能否继续测试？功能其实关闭能否拒绝？没有发生拖动是否仍会误判？错误对象是否也能满足断言？精确值错误是否会漏检？

静态检查能发现覆盖与证据缺口，不能证明真实模型误判率。只有实际设备和模型评估过的场景才能报告业务效果。
