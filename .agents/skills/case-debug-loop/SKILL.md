# 批量转换与调试循环（loop + goal）

把「一批源用例」推进到「全部忠实通过」：先批量转换，再逐条执行、分类失败、修复、重跑。本 Skill 只做编排——转换规则完整委托 [case-to-yaml](../case-to-yaml/SKILL.md)，执行命令完整委托 [run-case](../run-case/SKILL.md)，自身不复制二者的语法细节与命令映射。

## 定位契约

1. **定位项目**：以用户指定的 MTA 项目根目录为准；未指定时从工作目录向上定位同时包含 `ARCHITECTURE.md` 和 `midscene.config.ts` 的项目。
2. **确认前置**（与 run-case 相同）：项目根存在 `.env`（模型四项 `MIDSCENE_MODEL_*`）；目标平台设备已连接且独占。缺失时先提示配置，不带病启动。
3. **规模提示**：一批用例的串行真机执行加调试轮次可达数小时。开工前向用户说明预计耗时与设备独占要求，让用户决定现在跑还是分批跑。

## Goal：忠实通过

一条用例「成功」= `pnpm case` 退出码 0，**且**断言语义相对意图草稿未被放宽。只看退出码会奖励调绿——放宽断言、删验收点、加 `continue-on-error` 都能让循环更快收敛，但那是在销毁测试价值。两条硬规则保住 goal：

1. **改动留痕**：循环内每次修改 YAML 都记一条 before→after 改动及依据（因哪个失败而改、为何这样改），最终报告可逐条核对。
2. **放宽须确认**：放宽断言、删除验收点、降低验收阈值是对测试目标的修改，不在循环内静默执行——标记为待确认项，该用例转 `needs_clarification` 终态，继续其他用例，最终报告汇总请用户裁决。操作方式的适配（换控件描述、加显式等待、补导航步骤、修语法）不属于放宽，可直接修。

「断言语义未被放宽」以 case-to-yaml 的[断言策略](../case-to-yaml/references/assertion-policy.md)与意图草稿为基准：单断言单判定、判断对象限当前界面可观察证据、精确业务值保持精确。

## 失败分诊

循环里先分类再动手。只有前两类允许自动修：

| 失败类型 | 判定线索 | 循环动作 |
| --- | --- | --- |
| 编写缺陷 | YAML 语法、Node 输入不合法、生命周期钩子缺失、文件名含 glob 元字符、缺平台后缀、断言复合或跨界面 | 自动修，记改动记录 |
| 操作不适配 | 控件描述现场识别不到、异步界面未显式等待、缺导航步骤 | 自动修（适配操作方式，不动验收结果），记改动记录 |
| 验收结果不符 | 动作执行成功但业务结果与预期不符，且疑似放宽断言才能过 | 不修断言；标记待确认，转 `needs_clarification` |
| 疑似业务缺陷 | 断言正确表达了原文预期，现场证据显示被测系统不满足 | 不改用例；记证据，转 `real-failure`——这是测试的成果，不是要修的失败 |
| 环境问题 | 设备断连、`.env` 缺失、模型报错、会话建立失败 | 暂停整个循环（后续用例同环境，重试无意义），转 `env-blocked`，报告后等环境恢复续跑 |

判断「疑似业务缺陷」要克制：先排除设备 UI 版本差异与操作不适配（对照 examples/README 对设备敏感演示的既有经验），确认断言忠实于原文预期后再定性；拿不准时归入待确认，不冒充缺陷结论。

## Loop：状态机与台账

台账是循环的骨架：中断可续跑、超限能停、最终报告从台账直接生成。每个源用例一行，写入 `artifacts/case-debug-loop/<本次唯一目录>/progress.md`：

```text
drafted → static-ok → running → passed
                          ├→ real-failure        疑似业务缺陷（终态）
                          ├→ needs_clarification 待确认/放宽裁决（终态）
                          ├→ env-blocked         环境受阻（暂停，可续跑）
                          └→ exhausted           尝试超限未收敛（终态）
```

台账行模板：

```markdown
| 源用例 | YAML 路径 | 状态 | 尝试次数 | 最后失败分类 | 改动记录 |
| --- | --- | --- | --- | --- | --- |
| TC-001 登录 | cases/level2/account/login.android.yaml | running | 2 | 操作不适配 | #3 #5 |
```

改动记录逐条追加在同一目录的 `changes.md`：`#编号 | 用例 | 失败分类 | before → after | 依据`。

每轮硬性步骤：**先读台账 → 只推进一条用例 → 执行或修复 → 写回台账**。不整批重跑已通过的用例，不把全部转换记录读回上下文——上下文里只留台账摘要。

**限次规则**：每条用例执行尝试上限 3 次；同一失败分类连续 2 次修复未改善，提前转 `exhausted`，不烧设备磨。超限用例在报告中给出最后一次失败与已试改动。

## 流程

### 0. 一次性澄清（全程唯一需要用户介入的节点）

把这批用例的全部阻塞项汇总成一张清单一次问完，不逐条打断：平台与应用、包名、账号、设备角色与绑定（多设备用 DUT1/DUT2/DUT3 显式绑定）、验收阈值、证据路径、原文歧义、**落位**（目标 level 与模块目录，如 `cases/level2/account/`）。用户已明确回答的不重复确认。确实无法交互时，受影响用例标 `needs_clarification` 排除，其余独立用例继续。

### 1. 批量转换 + 静态检查（离线，便宜）

按 case-to-yaml 全流程一次批量转换全部用例：意图草稿、可判定断言、编译与静态检查，产物放置遵循其[转换交付契约](../case-to-yaml/references/conversion-contract.md)。可执行 YAML 直接写入第 0 步确定的 `cases/level*/<模块>/`（用户在澄清中已授权落位）——调试无法在 `artifacts/` 下进行：`pnpm case` 只接受 `cases/` 与 `examples/` 根内路径，且平台后缀（`.android.yaml` 等）决定执行项目。

本阶段把确定性错误全部修完：YAML 语法、Node 输入、生命周期钩子、文件命名（无 glob 元字符、带平台后缀）。设备时间只留给真正需要设备的阶段。完成后全部用例置 `static-ok`。

### 2. 试点 1 条

挑一条代表性用例（覆盖主要应用与典型动作模式）走完整个执行循环。系统性问题（包名、设备绑定、模型配置、等待模式）会在第一条上集中暴露，修一次惠及全部，好过 N 条各错一遍。试点的共性改动记入 `changes.md` 并注明适用范围。

### 3. 逐条执行循环

对每条 `static-ok` 用例：`pnpm case <单文件>` 执行 → 失败则读报告与结果明细（`midscene_run/report/`、`.midscene/test-results/<runId>/`）定位失败步骤 → 按分诊表分类 → 修复并记改动 → 写回台账 → 重跑。单文件执行天然按条隔离、失败归因清晰；绝不整批跑循环——每轮会把已通过的用例重烧一遍。

### 4. 收尾

1. **回归确认**：全部目标用例一次 `pnpm case <文件…>` 多文件执行（同一集合，不扩大范围），确认单条通过的结果在集合执行下依然成立。
2. **落位裁决**：`real-failure`、`needs_clarification`、`exhausted` 的用例留在 `cases/` 会污染后续批量入口的选择范围，报告中请用户决定保留、降级还是移出，不静默处置。
3. **汇总报告**：四栏交付——**通过**（忠实通过）、**疑似业务缺陷**（附证据与报告路径）、**待确认**（附放宽裁决请求）、**环境受阻**；附台账、改动记录（before→after 逐条可核对）与报告路径。生成或循环收敛不能表述为业务验收通过，验收结论由用户下。

## 边界与反模式

- 编排 Skill 不复制 case-to-yaml 与 run-case 的规则细节；转换按其契约执行，执行只经 `pnpm case`。生成、断言改写细节问 case-to-yaml 的职责范围，命令与失败语义问 run-case 的职责范围。
- 不新增执行面：单条/文件集走 `pnpm case`，套件级走既有 `MTA_SUITE=… pnpm test:cases:*`；不手工拼装官方 CLI 长命令，不设置 `MTA_CASE_FILES`。
- 不改造 Runtime、Node、Experience；修复只发生在用例 YAML 与编排产物内。
- 反模式：重试把 flaky 断言拖成通过（该用 `device.waitUntil` 显式等待）；循环内静默放宽断言；整批执行当调试循环；把疑似业务缺陷改写成通过；环境问题反复重试；把全部转换记录刷进上下文。
