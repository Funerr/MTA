## Why

普通测试人员需要从业务用例生成、理解并确认可执行 YAML，现有命令行与转换 Skill 尚未提供可视化编写闭环。引入轻量 Web 工作台，并在关键不确定点调用真实设备核查，让执行内容有来源、有现场依据且可人工修订。

## What Changes

- 提供结构化表单、整段粘贴及 Excel/Markdown/文本导入，统一呈现编号、名称、前置条件、步骤、预期和等级。
- 默认通过基本信息和步骤卡片编辑用例，保留原始用例及高级 YAML 视图；局部修改可追踪，人工编辑受到保护。
- 调用可配置模型生成意图草稿、平台执行工作流、覆盖关系和待澄清问题，复用现有 case-to-yaml 交付约定。
- 首版同时支持 Android 和 HarmonyOS，共享业务目标，分别维护执行内容与核查证据。
- 工作台作为现有 MTA 测试框架的可视化入口，将核查工作流提交至 MTA 项目配置、Runtime 与 Midscene Runner 执行链路；展示原生执行进度、截图、报告及修改建议，支持停止和人工接管。
- 对当前版本执行静态检查、人工确认和 YAML 导出，分别显示静态检查、设备核查和完整执行状态。

## Capabilities

### New Capabilities

- `case-authoring-workbench`: 结构化录入、模型转换、步骤视图与 YAML 同步、版本确认及导出。
- `authoring-device-verification`: 双平台编写核查、设备会话控制、证据关联与失效管理。

### Modified Capabilities

无。复用现有运行能力，不改变已有执行项目和 Node 的公开语义。

## Impact

- 新增本地 Web 前端、编写服务及本地草稿存储；具体依赖在实现前按项目环境核定。
- 复用 `.agents/skills/case-to-yaml/` 的转换规则；编写元数据保存在独立记录中，不扩展执行 YAML 字段。
- 复用 `src/setup/` 的设备会话和架构列出的 Adapter 边界；必要的通用适配收口须补充锁定依赖契约测试。
- 实施完成后更新使用文档；真实设备验收按平台独立记录日期、环境和覆盖范围。

## Non-goals

- 不建设拖拽流程图、云端设备集群、多用户协作或完整测试管理平台。
- 不自研 Runner/Planner，不在工作台循环派发节点或直接组织 Agent 动作；不新增业务 Node，不扩展冻结中的 Experience 大能力。
- 不因转换或确认自动运行完整用例；不将关键点核查宣称为业务验收通过。
